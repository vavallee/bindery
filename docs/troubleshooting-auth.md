# Auth Troubleshooting

Quick-reference for every auth-related symptom across all three auth phases. Each row maps to a risk mitigation identified during design — the "fix" column is what the mitigation actually looks like at runtime.

For setup guides, see the per-feature docs linked at the bottom.

## Symptom → cause → fix

| Symptom | Cause | Fix |
|---------|-------|-----|
| Bindery refuses to start: `proxy auth mode is active but BINDERY_TRUSTED_PROXY is empty` | Proxy mode was enabled but `BINDERY_TRUSTED_PROXY` is empty — Bindery refuses to start rather than silently allow any IP to set the identity header | Set `BINDERY_TRUSTED_PROXY` to your proxy's IP or CIDR (e.g. `172.20.0.0/16` for Docker bridge, `10.0.0.0/8` for Kubernetes pods). Bindery logs `proxy auth mode: trusted proxies` at startup with a `cidrs` field listing the effective list, so you can verify it. |
| Any LAN host can forge `X-Forwarded-User: admin` and get in | `BINDERY_TRUSTED_PROXY` is too broad (e.g. `0.0.0.0/0`) or empty while mode is somehow `proxy` | Tighten to only your proxy's IP or pod subnet. Confirm the effective CIDR list in the startup log line `proxy auth mode: trusted proxies`, whose `cidrs` field carries it. Firewall rules should ensure Bindery is unreachable except via the proxy. |
| `401 Unauthorized` after successful SSO login | Source IP not in `BINDERY_TRUSTED_PROXY`, or identity header name mismatch | (1) Check startup log for trusted CIDR — the request source IP (Traefik/Caddy container, not browser) must match. (2) Confirm `BINDERY_PROXY_AUTH_HEADER` matches what the proxy sends: Authelia → `Remote-User`; Authentik → `X-Authentik-Username`. Enable `BINDERY_LOG_LEVEL=debug` to log both. |
| Proxy mode login page shows "Sign in via your SSO provider" with nothing to click behind Cloudflare Tunnel or another proxy that sets `X-Forwarded-For`; log shows `identity header from untrusted source` | On 1.40.2 and earlier Bindery checked the visitor address from `X-Forwarded-For` against `BINDERY_TRUSTED_PROXY` instead of the proxy's own address (#3096) | Upgrade. Do not widen `BINDERY_TRUSTED_PROXY` to `0.0.0.0/0` to work around it: that lets any host forge the identity header. After the fix the warning reports `peer` (the connecting proxy, the address that must be in `BINDERY_TRUSTED_PROXY`) and `client` (the forwarded visitor) separately. Once it works, Bindery believes the identity header on every request from `cloudflared`, so every hostname and path the tunnel routes to Bindery must be covered by an Access application with no Bypass policy; an uncovered or bypassed path lets a visitor forge `Cf-Access-Authenticated-User-Email` and sign in as anyone. Bindery does not validate `Cf-Access-Jwt-Assertion`, which Cloudflare recommends. Other proxies must likewise remove or overwrite the header on every route; see [auth-proxy.md](auth-proxy.md#your-proxy-must-own-the-identity-header). |
| New Bindery user created every time a user renames their IdP account | Auto-provisioning keys on a mutable username/email header; rename produces a new row and orphans the old user's data | Use a stable, opaque identifier: Authelia internal UUID, Authentik user UUID, Keycloak `sub` claim. Configure `BINDERY_PROXY_AUTH_HEADER` to point at that header. There is no user merge. Delete the orphan from the **Users** page, reached from the header, and hand its library rows to the new account with `DELETE /api/v1/auth/users/<orphan-id>?strategy=reassign&reassignTo=<new-id>`. See [docs/auth-proxy.md — Header choice](auth-proxy.md#header-choice-stability-matters). |
| Two users at different IdPs map to the same Bindery account | Two providers can emit the same `sub` value for different people | This cannot happen by design — Bindery's user-mapping key is the composite `(oidc_issuer, oidc_sub)`, not `oidc_sub` alone. If you observe it, it is a bug; file an issue. |
| OIDC logout from IdP does not log out of Bindery | Bindery's HMAC-signed session cookie is independent of the IdP session; revoking the IdP session has no effect until the cookie TTL expires (~12h short-lived, up to 30d with "Remember me") | **Known limitation.** Session lifetime is fixed in the binary at 12 hours, or 30 days with "Remember me", and there is no setting for it. Rotate the session secret in Settings, General, Security. One rotation keeps the previous secret valid so nobody is dropped mid session; rotate a second time to stop every cookie signed under the original secret. To evict one account without touching anyone else, reset that user's password with `PUT /api/v1/auth/users/{id}/reset-password`, which bumps their session epoch. Logging out of Bindery on a device revokes that one session on the server; revoking a different device remotely is not built. |
| Rotating the session secret did not log anyone out | One rotation moves the old secret into the previous slot and cookies are verified against both, so existing logins survive on purpose | Rotate a second time. The second rotation overwrites the previous slot and every cookie signed under the original secret stops verifying. |
| OIDC client secret visible to anyone with DB read access | Client secrets are stored as plaintext in the `settings` table — same posture as indexer API keys | **Known limitation.** Protect `bindery.db` with `chmod 600`; restrict `kubectl exec` / `docker exec` access; treat backup files as sensitive. An env-var secret-ref pattern is planned for a future release. |
| User B can see User A's authors or books via API | A repository query is missing the `userID` filter — this is a bug; the `QueryScope` helper in the repo layer should catch it | File a bug report with the exact endpoint URL and response body. As a workaround, ensure user B does not have the `admin` role (admins can access all users' data by design). The two-user integration test matrix is the backstop to detect regressions. |
| `403 Forbidden` on API mutations that worked before v1.0 | CSRF double-submit token is now required for session-cookie-authenticated mutations | Switch the caller to `X-Api-Key` auth (exempt from CSRF), or add a `GET /api/v1/auth/csrf` preflight: `TOKEN=$(curl -s -b bindery_session=... http://bindery:8787/api/v1/auth/csrf \| jq -r .csrfToken)` then pass `-H "X-CSRF-Token: $TOKEN"`. |
| Existing API-key scripts break after v1.0 CSRF rollout | CSRF token incorrectly required on `X-Api-Key` requests | This should not happen — CSRF only applies when auth is session-cookie-based; `X-Api-Key` requests bypass it. If it does occur, it is a bug; file an issue. |
| A `403 Forbidden` you cannot explain, on any mutating request | One of the two CSRF guards (`X-Requested-With`, `X-CSRF-Token`) rejected it | Set the log level to debug (Settings → Logs, or `BINDERY_LOG_LEVEL=debug`) and repeat the request. The rejection logs `csrf guard: rejecting mutating request` with the guard that fired, the reason, and whether an API key, session cookie or CSRF token was present — values are never logged. If it says `api_key_query=true` with `api_key_header=false`, move the key from `?apikey=` into the `X-Api-Key` header: query-string keys are ignored on mutating methods. |
| In `local-only` or `disabled` mode, opening Bindery by a name such as `books.example.com` lands on the login page, and API calls answer `403` with an error naming `BINDERY_ALLOWED_HOSTS` | Those modes only skip the login for host names a public site cannot have (IP addresses, `localhost`, single label names, `.local`, `.lan`, `.home.arpa`, `.internal`, `.localdomain`, the host of `BINDERY_OIDC_REDIRECT_BASE_URL`). This guards against DNS rebinding, where a web page points its own name at Bindery's address | Add the name to `BINDERY_ALLOWED_HOSTS` (comma separated, `*.example.com` for a whole domain you own, never a shared one like `duckdns.org`) and restart. Tailscale `*.ts.net`, `.fritz.box` and Kubernetes names like `bindery.media.svc` need listing too. The log line `refused the login free grant` carries the exact name Bindery saw. Behind a reverse proxy that is the name the browser used. Signing in also works under any name. |
| Migration `025_multiuser.sql` fails mid-run | The pre-flight found library rows but no user account, so there is no user 1 to backfill ownership to. The `owner_user_id` columns are nullable, so there is no NOT NULL constraint to violate | The migration runs in a transaction — the DB is not corrupted on failure. Check the startup log for the printed repair query (typically a `DELETE FROM downloads WHERE book_id NOT IN (...)`). Run it, then restart. Always take a backup before upgrading — see [docs/upgrade-v1.md](upgrade-v1.md). |
| All data missing after v1.0 upgrade | Migration ran against the wrong database file | Confirm `BINDERY_DB_PATH` points to the correct file. Restore from the pre-upgrade backup. |
| Admin locked out — no admin account reachable | All user rows have `role='user'`, or admin account was deleted | Direct DB repair (no restart needed): `sqlite3 /config/bindery.db "UPDATE users SET role='admin' WHERE username='<name>';"` — Kubernetes: `kubectl exec deploy/bindery -- sqlite3 /config/bindery.db "UPDATE users SET role='admin' WHERE id=1;"` |
